# 웹서비스 설계 개발 기록

## 1. 프로젝트 개요

**진행일:** 2026.10.28

**과제명:** JWT 인증을 적용한 나만의 게시판 만들기

**서비스명:** Mario Secret Guide — 닌텐도 DS 슈퍼마리오 비밀 맵 공략 게시판

**기술 스택**

| 구분 | 사용 기술 |
|---|---|
| 프론트엔드 | React, Vite, JavaScript |
| 백엔드 | Python, FastAPI, Uvicorn |
| 데이터베이스 | SQLite |
| 인증 방식 | JWT, HS256 |
| 개발 환경 | macOS, VS Code, Chrome |
| 개발 서버 | React 5173, FastAPI 8000 |
| 최종 검증 주소 | http://127.0.0.1:4173 |

### 개발 목적

본 프로젝트는 뉴 슈퍼 마리오브라더스 DS의 숨겨진 월드와 비밀 출구 공략을 공유하는 웹서비스이다.

기존 게시판 CRUD 기능에 JWT 기반 사용자 인증과 작성자 권한 검사를 연결하여 다음 기능을 구현하는 것을 목표로 하였다.

- 로그인하지 않은 사용자도 공략 게시글 조회 가능
- 로그인한 사용자만 공략 게시글 작성 가능
- 자신이 작성한 게시글만 수정·삭제 가능
- JWT를 이용한 사용자 인증 및 토큰 만료 처리
- 게시글 데이터 저장과 서버 재시작 후 데이터 유지

과제에서 제공된 기본 CRUD 및 데이터 저장 코드를 활용하고, JWT 인증·권한 검사와 React 인증 연동 기능을 완성하였다.

## 2. 개발 환경 구축

**진행일:** 2026.10.28

### 진행 내용

프론트엔드는 React와 Vite, 백엔드는 Python과 FastAPI를 선택하였다.

프론트엔드와 백엔드는 서로 다른 실행 환경을 사용하므로 각각 의존성을 설치하고 서버를 실행하였다.

**FastAPI 백엔드**

```bash
cd backend-fastapi
.venv/bin/python -m uvicorn app:app --host 127.0.0.1 --port 8000
```

**React 프론트엔드**

```bash
cd frontend-react
npm ci
npm run dev
```

**동작 확인**

`GET http://127.0.0.1:8000/api/health`

실제 응답: HTTP 200 OK

### 발생한 문제 및 해결

**문제:** FastAPI 실행 중 `Errno 48: address already in use` 발생

**원인 추정:** 기존 캡스톤 프로젝트에서 실행한 서버가 이미 8000번 포트를 사용하고 있었다.

**시도:** 기존에 실행 중인 서버 프로세스를 확인하였다.

**최종 해결:** 기존 서버를 종료한 뒤 FastAPI 서버를 다시 실행하였다.

**검증:** `GET /api/health` 요청에서 HTTP 200 OK 및 정상 상태 응답 확인

**교훈:** 서버가 실행되지 않는다고 해서 코드에 오류가 있는 것은 아니며, 포트 점유 상태와 실행 환경도 함께 확인해야 한다.

## 3. 기존 CRUD 기능 사전 검증

### 진행 목적

JWT 인증을 구현하기 전에 과제에서 제공한 기본 게시판 기능이 정상적으로 작동하는지 확인하였다.

### 사전 검증 결과

| 기능 | 검증 결과 | HTTP 응답 |
|---|---|---|
| 게시글 등록 | 화면에서 등록 성공 확인 | 초기 HTTP 미확인 |
| 게시글 목록 조회 | 목록 표시 확인 | 200 |
| 게시글 수정 | 수정 내용 화면 반영 | 200 |
| 게시글 삭제 | 삭제 후 목록에서 제거 | 204 |
| 삭제 후 새로고침 | 게시글 목록 0개 유지 | 초기 HTTP 미확인 |

### 확인 내용

기존 게시판의 목록·상세 조회, 등록, 수정, 삭제 기능이 기본적으로 제공되어 있음을 확인하였다.

다만 초기 상태에서는 JWT 인증이 완성되지 않았으며, 데모 작성자로 게시글이 처리되거나 사용자별 권한 검사가 연결되지 않은 상태였다.

따라서 이후 개발 과정에서는 기존 CRUD 코드를 새로 작성하기보다 JWT 인증과 작성자 권한 검사를 연결하는 작업을 중심으로 진행하였다.

## 4. JWT 비밀 키 및 환경변수 설정

### 진행 목적

서버에서 JWT를 안전하게 발급하고 검증하기 위해 서명에 사용할 비밀 키를 설정하였다.

### 관련 파일

`backend-fastapi/.env`

`backend-fastapi/auth.py`

### 구현 과정

Python의 `secrets` 모듈을 이용하여 무작위 32바이트 키를 생성하고, 이를 64자리 16진수 문자열로 환경변수에 저장하는 방법을 적용하였다.

JWT 관련 환경변수는 다음과 같다.

| 환경변수 | 역할 |
|---|---|
| JWT_SECRET | HS256 서명 및 검증에 사용되는 비밀 키 |
| JWT_ISSUER | 토큰 발급자 |
| JWT_AUDIENCE | 토큰 사용 대상 |
| TOKEN_TTL | 토큰 유효 시간 |

기본 JWT 유효 시간은 90초로 설정하였다.

### 검증 결과

환경변수 형식 검증을 수행하고 JWT 발급 및 검증 요청을 테스트하였다.

이후 정상 로그인에서 JWT 발급에 성공하였으며, 변조된 JWT는 401 INVALID_TOKEN으로 거부되는 것을 확인하였다.

**보안 사항:** 실제 JWT_SECRET 값은 개발 기록 및 제출 보고서에 포함하지 않는다.

## 5. FastAPI JWT 백엔드 구현

### 5.1 JWT 발급 기능 구현

**관련 파일:** `backend-fastapi/auth.py`

**관련 함수:** `issue_token(user)`

**구현 내용**

로그인에 성공한 사용자에게 JWT를 발급하도록 미완성 기능을 구현하였다.

JWT 페이로드에는 다음 정보를 포함하였다.

| 클레임 | 역할 |
|---|---|
| sub | 인증된 사용자 ID |
| exp | 토큰 만료 시각 |
| iss | 토큰 발급자 |
| aud | 토큰 사용 대상 |

서명 알고리즘은 HS256을 사용하였다.

**검증 결과**

Alice 계정으로 정상 로그인한 결과 HTTP 200 OK가 반환되었다.

응답 JSON에서 `accessToken`, `expiresIn`, `user` 정보를 확인하였다.

### 5.2 JWT 검증 기능 구현

**관련 파일:** `backend-fastapi/auth.py`

**관련 함수:** `current_user_id(request)`

**구현 내용**

보호 API에 전달된 Authorization 헤더에서 Bearer 토큰을 추출하고 다음 항목을 검증하도록 구현하였다.

- JWT 서명과 HS256 알고리즘
- exp 만료 여부 및 필수 클레임
- iss 발급자
- aud 사용 대상
- sub 사용자 ID
- 실제 사용자 계정 존재 여부

정상 JWT는 사용자 ID를 반환하여 다음 API 처리 단계에서 사용하도록 하였다.

### JWT 검증 결과

| 상황 | 실제 HTTP | JSON code |
|---|---|---|
| 정상 JWT | 200 | 해당 없음 |
| 토큰 없음 | 401 | TOKEN_REQUIRED |
| 서명 변조 | 401 | INVALID_TOKEN |
| 토큰 만료 | 401 | TOKEN_EXPIRED |

**교훈:** JWT의 내용을 읽을 수 있다는 것과 토큰의 서명·만료 조건이 유효하다는 것은 서로 다르다. 보호 API에서는 반드시 서명과 클레임을 검증해야 한다.

### 5.3 작성자 권한 검사

**관련 파일:** `backend-fastapi/auth.py`

**관련 함수:** `assert_owner(user_id, author_id)`

**구현 내용**

게시글 수정·삭제 요청에서 JWT로 인증한 사용자 ID와 게시글의 실제 작성자 ID를 비교하도록 구현하였다.

두 값이 일치하면 요청을 허용하고, 일치하지 않으면 403 FORBIDDEN을 반환하도록 하였다.

**검증 결과**

Bob이 Alice의 게시글을 수정하거나 삭제하도록 요청한 결과 두 요청 모두 403 FORBIDDEN으로 거부되었다.

이후 게시글을 재조회하여 원본이 유지되는 것도 확인하였다.

## 6. React와 JWT 인증 연동

### 6.1 로그인 및 토큰 저장

**관련 파일:** `frontend-react/src/api.js`

**관련 함수:** `login()`

**구현 내용**

React 로그인 폼에서 입력받은 이메일과 비밀번호를 FastAPI의 로그인 API로 전달하도록 구현하였다.

로그인 성공 시 서버 응답의 `accessToken`과 사용자 정보를 JavaScript 메모리에 저장하도록 수정하였다.

**검증 결과**

Alice 로그인 성공 시 사용자 이름이 화면에 표시되었으며, 정상 JWT가 발급되는 것을 확인하였다.

### 6.2 Authorization Bearer 헤더 전송

**관련 파일:** `frontend-react/src/api.js`

**관련 함수:** `authorizationHeaders()`

**구현 내용**

로그인된 사용자의 JWT를 보호 API 요청에 자동으로 첨부하도록 구현하였다.

```text
Authorization: Bearer <JWT>
```

JWT가 없을 경우 Authorization 헤더를 추가하지 않도록 처리하였다.

**검증 결과**

로그인 후 `/api/me` 요청에서 Authorization 헤더가 전송되는 것을 확인하였다.

정상 JWT를 사용한 요청은 HTTP 200과 사용자 정보를 반환하였다.

### 6.3 인증 실패 및 세션 초기화

**관련 파일:** `frontend-react/src/api.js`

**관련 함수:** `request()`, `clearSession()`

**구현 내용**

FastAPI에서 HTTP 401을 반환하면 React 메모리의 JWT와 사용자 정보를 제거하여 로그인 상태를 해제하도록 수정하였다.

**검증 결과**

유효 시간이 지난 JWT를 이용해 `/api/me`를 요청한 결과 401 TOKEN_EXPIRED가 반환되었다.

React 화면에서도 로그인 상태가 해제되는 것을 확인하였다.

또한 로그아웃 후 `/api/me` 요청에서 401 TOKEN_REQUIRED가 반환되는 것을 확인하였다.

### 6.4 작성자별 수정·삭제 버튼 표시

**관련 파일:** `frontend-react/src/api.js`

**관련 함수:** `canEdit()`

**구현 내용**

현재 로그인한 사용자 ID와 게시글 작성자 ID를 비교하여 작성자 본인에게만 수정·삭제 버튼을 표시하도록 변경하였다.

서버의 `assert_owner()`와 프론트엔드의 `canEdit()`가 서로 다른 역할을 수행하도록 구성하였다.

**교훈:** 프론트엔드의 버튼 숨김은 사용자 인터페이스 제어이며, 실제 보안은 백엔드의 작성자 권한 검사로 보장해야 한다.

### 6.5 비로그인 게시글 작성 제한

**관련 파일:** `frontend-react/src/main.jsx`

**관련 함수:** `save()`

**구현 내용**

비로그인 상태에서 게시글 등록을 시도하면 로그인 안내를 표시하도록 수정하였다.

```javascript
if (!getSession().accessToken) {
  setMessage("게시글을 작성하려면 먼저 로그인하세요.");
  return;
}
```

프론트엔드 검사와 별개로 FastAPI에서도 토큰 없는 게시글 등록 요청을 401 TOKEN_REQUIRED로 거부하도록 구성하였다.

## 8. JWT 및 게시판 기능 통합 테스트

**진행일:** 2026.10.28

**검증 환경**

- React 빌드 미리보기: http://127.0.0.1:4173
- FastAPI: http://127.0.0.1:8000
- Chrome 개발자 도구: Network, Console

T01~T17 테스트를 수행하면서 실제 HTTP 상태와 JSON 오류 코드를 확인하였다.

### 테스트 결과 요약

| ID | 검증 항목 | 실제 결과 | 판정 |
|---|---|---|---|
| T01 | 비로그인 공개 게시글 조회 | GET 200 / 해당 없음 | PASS |
| T02 | Alice 정상 로그인 | 200 / 해당 없음, JWT 발급 | PASS |
| T03 | 잘못된 계정·비밀번호 | 401 / INVALID_CREDENTIALS | PASS |
| T04 | 토큰 없는 보호 API 요청 | 401 / TOKEN_REQUIRED | PASS |
| T05 | Alice 게시글 등록·내 정보 조회 | POST 201, GET 200 | PASS |
| T06 | Alice 본인 글 수정·삭제 | PUT 200, DELETE 204 | PASS |
| T07 | Bob의 Alice 글 수정 시도 | 403 / FORBIDDEN, 원본 유지 | PASS |
| T08 | Bob의 Alice 글 삭제 시도 | 403 / FORBIDDEN, 원본 유지 | PASS |
| T09 | 변조 JWT 요청 | GET·POST·PUT·DELETE 모두 401 / INVALID_TOKEN | PASS |
| T10 | 만료 JWT 요청 | GET·POST·PUT·DELETE 모두 401 / TOKEN_EXPIRED | PASS |
| T11 | 로그아웃 후 내 정보 조회 | 401 / TOKEN_REQUIRED | PASS |
| T12 | authorId·userId 위조 | 각각 400 / BAD_INPUT, 데이터 유지 | PASS |
| T13 | 빈 제목·공백 본문·길이 초과 | 모두 400 / BAD_INPUT, 데이터 유지 | PASS |
| T14 | 없는 글 및 잘못된 ID 요청 | 404 / NOT_FOUND, 400 / BAD_INPUT | PASS |
| T15 | 서버 재시작 후 게시글 유지 | 등록 201, 재조회 200 | PASS |

| T17 | 무토큰 요청 및 Bob의 정상 CRUD | 401, 201, 200, 204 확인 | PASS |

### 주요 세부 검증

**작성자 권한 테스트**

Alice의 게시글 ID 3에 대해 Bob의 정상 JWT로 수정·삭제를 시도하였다.

두 요청은 403 FORBIDDEN으로 거부되었으며, 이후 공개 조회에서 원본이 유지되었다.

**JWT 변조 테스트**

정상 발급된 JWT의 서명 일부를 변경한 후 GET·POST·PUT·DELETE 요청을 전송하였다.

모두 401 INVALID_TOKEN으로 거부되었으며 데이터가 변경되지 않았다.

**JWT 만료 테스트**

FastAPI 서버의 TOKEN_TTL을 3초로 설정하고 JWT를 발급하였다.

실제 만료 후 보호 API 요청에서 401 TOKEN_EXPIRED가 반환되었다.

테스트 후 JWT 유효 시간을 기본값인 90초로 복구하였다.

**작성자 ID 위조 방지**

Bob의 정상 JWT를 사용하고 게시글 등록 본문에 `authorId: 1`, `userId: 1`을 각각 추가하였다.

두 요청 모두 400 BAD_INPUT으로 거부되었으며, 게시글 목록이 변경되지 않았다.

**입력값 검증**

빈 제목, 공백 3칸의 본문, 제목 101자, 본문 5001자를 각각 전송하였다.

네 요청 모두 400 BAD_INPUT으로 거부되었으며 새로운 게시글이 생성되지 않았다.

### HTTP 응답 코드 정리

| HTTP | JSON code | 의미 |
|---|---|---|
| 200 | 해당 없음 | 조회·로그인·수정 성공 |
| 201 | 해당 없음 | 게시글 생성 성공 |
| 204 | 해당 없음 | 게시글 삭제 성공 |
| 400 | BAD_INPUT | 입력값 또는 ID 형식 오류 |
| 401 | INVALID_CREDENTIALS | 로그인 계정 정보 불일치 |
| 401 | TOKEN_REQUIRED | JWT 누락 또는 Bearer 형식 오류 |
| 401 | INVALID_TOKEN | 변조 또는 잘못된 JWT |
| 401 | TOKEN_EXPIRED | JWT 만료 |
| 403 | FORBIDDEN | 인증된 사용자에게 변경 권한 없음 |
| 404 | NOT_FOUND | 게시글이 존재하지 않음 |

## 11. 추가 인증 처리 우선순위 검증

### 검증 목적

동일하게 존재하지 않는 게시글 ID 1003을 대상으로 JWT 유무에 따라 서버의 응답이 달라지는지 확인하였다.

### 실제 결과

| 조건 | 요청 | 실제 HTTP와 code |
|---|---|---|
| Alice 정상 JWT | PUT /api/posts/1003 | 404 / NOT_FOUND |
| JWT 없음 | PUT /api/posts/1003 | 401 / TOKEN_REQUIRED |

JWT가 없는 요청에서는 게시글의 존재 여부에 앞서 인증 실패 응답이 반환되었다.

반면 정상 JWT로 동일한 요청을 전송하면 인증을 통과한 다음 게시글이 존재하지 않는다는 404 NOT_FOUND 응답이 반환되었다.

**검증 결과:** 정상 작동 확인

**관련 증거:** 그림 27, 그림 35

## 12. 개발 과정에서 확인한 문제와 해결

### 문제 1. FastAPI 실행 포트 충돌

**문제 및 증상:** Uvicorn 실행 과정에서 `Errno 48: address already in use` 발생

**원인 추정:** 기존 프로젝트 서버가 8000번 포트를 사용하고 있었다.

**시도:** 기존 실행 프로세스 및 서버 상태 확인

**최종 해결:** 기존 서버를 종료하고 FastAPI 서버 재실행

**검증:** GET /api/health → HTTP 200 OK

**교훈:** 서버 실행 오류 발생 시 코드뿐 아니라 포트 및 프로세스 상태를 확인해야 한다.

### 문제 2. React에서 인증 없는 내 정보 조회 요청

**문제 및 증상:** 브라우저 Network에서 GET /api/me 요청이 401 Unauthorized로 나타남

**원인 확인:** 인증에 필요한 JWT가 요청에 포함되지 않은 경우 서버가 TOKEN_REQUIRED를 반환함.

**시도:** 로그인 응답에서 토큰 발급 여부와 Request Headers의 Authorization 항목 확인

**최종 해결:** React의 로그인 세션과 authorizationHeaders()를 연결하여 정상 JWT를 보호 요청에 첨부하도록 수정

**검증:** 정상 로그인 후 GET /api/me 요청에서 HTTP 200 OK와 Alice 사용자 정보 확인

**교훈:** 백엔드에서 JWT를 발급하는 기능과 프론트엔드에서 JWT를 저장·전송하는 기능이 모두 연결되어야 인증이 완성된다.

### 문제 3. JWT 만료 및 로그인 상태 처리

**문제 및 증상:** JWT가 만료되면 보호 API 호출에서 HTTP 401 반환

**원인 확인:** JWT의 exp 시각이 지나 서버에서 해당 토큰을 유효하지 않은 인증 정보로 처리함.

**시도:** 짧은 TTL 3초로 토큰을 발급하고 실제 만료 후 API 요청 수행

**최종 처리:** HTTP 401 응답 시 React 세션을 초기화하고 로그아웃 상태로 전환

**검증:** 401 TOKEN_EXPIRED 및 화면 로그아웃 상태 확인

**교훈:** 서버에서 인증을 거부하는 것과 프론트엔드에서 로그인 상태를 변경하는 것은 별도의 처리이므로 함께 구현해야 한다.

## 17. 현재 한계 및 개선 사항

이번 과제의 필수 JWT 인증과 게시글 권한 검사 기능은 수동 테스트를 통해 검증하였다.

다만 다음과 같은 개선 여지가 있다.

### JWT 관리

현재 JWT는 브라우저 메모리에 보관된다.

로그아웃하더라도 외부에 복사된 정상 JWT는 만료 전까지 사용될 수 있으므로, 향후 서버 측 토큰 철회 기능을 추가하는 방안을 검토할 수 있다.

### 테스트 자동화

현재 주요 검증은 Chrome 개발자 도구와 직접 API 요청을 이용한 수동 테스트를 중심으로 수행하였다.

향후 pytest 등 자동화 도구를 이용하여 인증·권한·입력값 검증을 반복적으로 실행할 수 있도록 개선할 수 있다.

### 게임 공략 기능

현재는 슈퍼마리오 비밀 맵 공략을 공유할 수 있는 기본 게시판이다.

향후 월드별 분류, 공략 검색, 이미지 첨부 기능 등을 추가하면 게임 공략 서비스의 목적을 더욱 명확하게 구현할 수 있다.

## 18. 최종 회고

이번 프로젝트를 진행하면서 프론트엔드, 백엔드, 데이터베이스가 서로 다른 역할을 수행하며 HTTP API를 통해 연결된다는 것을 이해하였다.

특히 JWT 인증을 구현하는 과정에서 로그인 성공 시 토큰을 발급하는 것만으로는 인증 기능이 완성되지 않는다는 점을 알게 되었다.

백엔드는 요청마다 JWT를 검증해야 하고, 프론트엔드는 발급된 토큰을 저장하고 필요한 요청에 첨부해야 한다. 또한 권한이 없는 사용자가 API를 직접 호출할 수 있으므로, 실제 권한 검사는 백엔드에서 수행해야 한다는 것을 배웠다.

T01~T17 테스트를 수행하면서 HTTP 200·201·204뿐 아니라 400·401·403·404 응답의 의미를 구분하고, 요청이 실패한 후에도 기존 데이터가 변경되지 않았는지 확인하는 과정의 중요성을 이해하였다.

결과적으로 기존 CRUD 게시판에 JWT 인증과 작성자 권한 검사를 연결하고, 서버와 브라우저의 동작을 실제 HTTP 요청으로 검증하는 경험을 할 수 있었다.
